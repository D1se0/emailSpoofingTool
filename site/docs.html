🔍 analyze — análisis completo

El comando central. Ejecuta todas las comprobaciones DNS en cadena y produce el score 0–100, el grado, los vectores viables, los hallazgos y el plan de acción. Nunca envía nada.

Sintaxis

python3 mailforge.py analyze <dominio> [--save] [--no-banner]
Arg/flagObligatorioDescripción
<dominio>sídominio a auditar. Sin http://, sin www, solo el dominio.
--savenoguarda el informe JSON en reports/ con timestamp

Ejemplo de prueba completo (datos ficticios)

   Subdomain escape (80%) · Display-name (30%)

Qué comprueba exactamente

  1. SPF: registro TXT, mecanismos, política all, límite de 10 lookups, redirect= (lo sigue), ptr (avisa).
  2. DKIM: sondea ~60 selectores comunes (incluye estilo fechas de Google: 20230601…), sigue CNAMEs, detecta claves revocadas (p= vacío), wildcards vacíos y fuerza <2048 bits.
  3. DMARC: _dmarc.midominio.com y, si no existe, el del dominio organizacional (p. ej. midominio.co.uk hereda de midominio.co.uk, no de co.uk).
  4. DNSSEC: DS en la zona padre + AD bit + RRSIG + DNSKEY (triple comprobación).
  5. STARTTLS real: se conecta a tus MX y negocia TLS de verdad; lee MTA-STS y TLS-RPT; BIMI.

🧾 compose — compositor libre, parámetro a parámetro

Este comando construye el mensaje exacto que defines campo a campo, te lo muestra como .eml, te genera los comandos para inyectarlo tú… y con --send lo envía de verdad ejecutando swaks por detrás. Pensado para que cualquiera pueda usarlo: cada parámetro está explicado abajo con ejemplos simples y avanzados.

Sintaxis completa

python3 mailforge.py compose \
    --from-name "<NOMBRE VISIBLE>" \
    --from-email "<EMAIL DE ENVÍO>" \
    --to "<EMAIL DESTINATARIO>" \
    --subject "<ASUNTO>" \
    --text "<CUERPO/DESCRIPCIÓN>" \
  [ --reply-to "<reply@ajeno.com>" ]            # cabecera Reply-To distinta
  [ --attach fichero1.pdf --attach foto.png ]   # adjuntos reales (máx 10)
  [ --priority high|normal|low ]                # X-Priority 1 / 3 / 5
  [ --relay smtp.turelay.com --port 25|587 ]    # servidor de salida
  [ --smtp-user usuario ]                       # login del relay (pass por env)
  [ --no-tls | --tls-optional | --tls-only ]    # cifrado del canal
  [ --save drill.eml ]                          # guarda el .eml en disco
  [ --send ]                                    # ENVÍO REAL vía swaks

📌 Referencia de cada parámetro

--from-name · nombre visible

Qué es (nivel cero): el nombre que el destinatario ve como remitente en su bandeja, antes de abrir el correo. Es cosmético: no participa en la autenticación. Por detrás: se codifica con RFC 2047 (=?utf-8?q?…=) para soportar acentos; la librería email de Python (EmailMessage + formataddr) construye el mensaje. Si lo omites, se usa la propia dirección como nombre.

# simple:
--from-name "Carlos"
# avanzado (acentos y cargo — codificado automáticamente):
--from-name "CE0 Carlos Pérez (Dirección Financiera)"

--from-email · dirección de envío obligatorio

Qué es: la dirección del cabecero From: — la que el receptor evalúa contra DMARC y cuyo dominio es el "suplantado". Por detrás: define el dominio del Message-ID y del saludo EHLO; DMARC compara este dominio con el del sobre SMTP y con el firmado por DKIM (alineación). Un dominio sin MX hará fallar el envío.

# simple:
--from-email jefe@midominio.com
# avanzado — prueba de suplantación por subdominio (decide el sp= de DMARC):
--from-email soporte@sub.midominio.com

--to · destinatario obligatorio

Qué es: el buzón que recibe el mensaje — debe ser tuyo o con consentimiento: tu buzón corporativo, un alias propio o un temporal de prueba (Guerrilla Mail). Por detrás: al enviar, MailForge resuelve los registros MX del dominio del destinatario con su stack DNS (UDP→TCP→DoH) para saber a qué servidor entregar; también puedes fijarlo con --relay.

# simple:
--to test@midominio.com
# avanzado — buzón temporal con etiqueta +tag (drill desechable):
--to yvt0wp+77xiollatz23c@sharklasers.com

--subject · asunto

Qué es: la línea de asunto — donde vive la ingeniería social de un ataque real ("URGENTE", "Factura vencida"…). Por detrás: recortado a 998 caracteres (RFC 5322) y codificado RFC 2047 si lleva acentos.

# simple: --subject "Hola"
# avanzado (encadenado realista de respuestas):
--subject "RE: RE: FW: Factura #4471 — pago pendiente"

--text · cuerpo

Qué es: el contenido del correo. Por detrás: parte MIME text/plain; charset=utf-8 con Content-Transfer-Encoding: base64 (los acentos sobreviven a cualquier servidor). Máx. 100.000 caracteres.

# simple: --text "Hola, esto es una prueba."
# avanzado (cuerpo multilínea desde un fichero):
--text "$(cat cuerpo.txt)"

--reply-to · dirección de respuesta opcional

Qué es: cabecera Reply-To: — al pulsar "Responder", la respuesta va AQUÍ y no al From. Técnica real de ataque: From suplantado + Reply-To ajeno. Si tu pasarela no alerta de esto, es un hallazgo.

# avanzado (técnica de robo de respuestas):
--reply-to recogida@otro-correo.com

--attach · adjuntos opcional · repetible · máx 10

Qué es: ficheros que viajan dentro del correo (PDF, PNG, ZIP…). Por detrás: cada uno se embebe como parte MIME con Content-Disposition: attachment; filename="…" y su MIME type autodetectado, convirtiendo el mensaje en multipart/mixed. En la web se suben en base64 (límite ~6 MB total). Un adjunto corrupto se omite con warning sin romper el mensaje.

# simple: --attach factura.pdf
# avanzado (tres partes en un mensaje):
--attach factura.pdf --attach logo.png --attach datos.csv

--priority · urgencia opcional

Qué es: marca el correo como urgente (muchos clientes lo resaltan). Por detrás: high → X-Priority: 1 + Importance: High; low → X-Priority: 5; normal no añade nada.

--relay, --port, --smtp-user · servidor de salida opcional

Qué es: a qué SMTP se conecta MailForge. Sin --relay entrega directamente al MX del destinatario (como un atacante real). ¿Cuándo usar relay? Cuando tu red doméstica/cloud bloquea el puerto 25 saliente (lo habitual) o para enviar desde tu infraestructura autorizada.

--relay smtp.midominio.com --port 587 --smtp-user drill@midominio.com
# la contraseña va por variable de entorno (nunca en el historial):
export MAILFORGE_SMTP_PASS="tu-clave"

--no-tls / --tls-optional / --tls-only · cifrado opcional

Por detrás: tls (por defecto) → swaks -tls (STARTTLS oportunista, como un emisor real); tls-optional → continúa aunque no haya TLS; tls-only → aborta si no hay TLS; no-tls → texto claro.

🚀 Envío real — cómo la herramienta envía por ti (swaks por detrás)

Con --send (CLI) o el botón “✉ Enviar AHORA (real, vía swaks)” del Spoof Lab, MailForge ejecuta el envío por ti: tú solo rellenas los campos. Así funciona exactamente lo que ocurre por detrás:

  1. Composición — compose_spoof_email() construye tu mensaje RFC 5322 exacto (cabeceras, MIME, adjuntos) y lo escribe en un fichero temporal con permisos 0600.
  2. Resolución del destino — consulta DNS (UDP→TCP→DoH) los registros MX del dominio del destinatario; si fijaste --relay, usa el tuyo.
  3. Ejecución de swaks — invoca el binario con una lista de argumentos (nunca shell → imposible inyectar comandos): swaks --to … --from … --ehlo … --server <MX> --port 25 -tls --data @/tmp/mf-drill-*.eml. El --data @fichero entrega tu .eml byte a byte.
  4. Transcripción y veredicto — el parser lee la conversación SMTP (<~ respuestas, ** errores) y el código de fin-de-DATA decide: 250 → ✅ ACEPTADO · 5xx → ⛔ RECHAZADO · 4xx → ⚠ transitorio. Todo se muestra en pantalla.
  5. Limpieza — el .eml temporal se borra siempre, incluso si hay error.

Flujo completo

   TÚ (compose --send / botón web "Enviar AHORA")
        │  from-name, from-email, to, subject, text, adjuntos…
        ▼
   MailForge core (Python)
        │  1. compose_spoof_email() → .eml exacto (tmp, 0600)
        │  2. DNS: MX del destinatario (p.ej. mail.guerrillamail.com)
        │  3. subprocess SIN shell:
        │       swaks --to <dest> --from <remitente> --ehlo <dominio>
        │             --server <MX> --port 25 -tls --data @/tmp/mf-drill-*.eml
        ▼
   Servidor SMTP del destinatario
        │  220 banner → EHLO → STARTTLS → MAIL FROM → RCPT TO → DATA
        ▼
   Veredicto parseado de la transcripción
        ├─ 250 → ✅ ACEPTADO (encolado) → depende de filtros: INBOX/spam
        ├─ 5xx → ⛔ RECHAZADO (protección activa: DMARC p=reject)
        └─ 4xx → ⚠ error transitorio (reintenta más tarde)

¿Qué pasa después de que el servidor acepte?

El mensaje llega al buzón y el receptor estampa su veredicto en las cabeceras. Ábrelo y busca Authentication-Results::

Authentication-Results: mx.destinatario.com;
   spf=fail (sender IP is 203.0.113.7) smtp.mailfrom=midominio.com;
   dkim=none (no signature);
   dmarc=none action=none header.from=midominio.com

dmarc=none action=none + mensaje en INBOX → tu dominio es suplantable ❗ → ejecuta harden. Tras aplicarlo, el mismo drill dará dmarc=fail action=quarantine/reject o un 550 directo.

🚀 drill — ENVÍO REAL con veredicto del servidor

⚠ Este comando envía un email de verdad. Solo apunta a un buzón del dominio que analizas y declaras tuyo (el guard lo bloquea si no). Es tu equivalente local del "test de entrega" de emkei.cz, pero defensivo: el objetivo es comprobar si TU dominio resiste la suplantación.

Sintaxis completa

python3 mailforge.py drill <dominio> <buzon@dominio>
       [--motif invoice|password|giftcard]
       [--exec "CE0 Carlos Pérez"]
       [--relay smtp.turelay.com] [--port 587]
       [--imap imap.midominio.com[/jefe@midominio.com] [--imap-wait 45]]
       [--yes]
FlagPor defectoDescripción
--motifinvoiceplantilla de ingeniería social del drill
--exec"CEO"nombre del directivo suplantado en el From:
--relayMX del dominiotu propio relay. Sin este flag, MailForge entrega directamente al MX del dominio analizado (como haría el atacante).
--port25puerto SMTP del relay (587 con STARTTLS si usas auth)
--imap—host[/usuario] para verificar por IMAP dónde aterrizó (INBOX vs spam)
--imap-wait20segundos de espera antes de la consulta IMAP
--yesnosalta la confirmación interactiva (para scripts)

Ejemplo 1 — directo al MX del dominio (simula al atacante real)

🧾 Recetas completas (de principio a fin)

Receta A — auditar y blindar tu dominio en 30 minutos

  1. Baseline: analyze midominio.com → anota score (p. ej. 34/D).
  2. Predecir el daño: spooftest midominio.com invoice → verás "INBOX — suplantable".
  3. Generar defensas: harden midominio.com → publica los 6 registros en tu DNS.
  4. Firmar DKIM: sigue la guía impresa por harden (opendkim-genkey, dos selectores s1/s2).
  5. Rollout DMARC: rollout midominio.com → publica FASE 0 hoy, sube cada 2-4 semanas.
  6. Confirmar empíricamente: drill midominio.com jefe@midominio.com --imap imap.midominio.com --yes → debe pasar de "ACEPTADO" a "RECHAZADO 550".
  7. Verificar llegada: el chequeo IMAP no debe encontrar el mensaje (fue rechazado).
  8. Re-auditar: analyze midominio.com → objetivo A (≥85). Guarda el HTML: report midominio.com html.

Receta B — demostración para tu dirección (sin tocar producción)

  1. spooftest midominio.com password en pantalla durante la reunión: el mensaje suplantado + veredicto.
  2. Si el veredicto es "INBOX", ejecuta el drill real a TU buzón: cuando llegue al inbox delante de todos, queda claro el riesgo.
  3. Cierra con report midominio.com html y el plan de hardening.

🔬 Arquitectura interna (para curiosos y auditores)

mailforge.py (CLI Rich)          server/index.js (API Node)        web/ (React)
        │                               │  JSON sobre HTTP            │
        └───────────────┬───────────────┴──────────────┬──────────────┘
                        ▼                              ▼
                     api.py  ◄──── puente JSON (##JSON##) ────►  callCore()
                        │
        ┌───────────────┼───────────────────────────────┐
        ▼               ▼                               ▼
   core/dnsx.py    core/spf|dkim|dmarc.py          core/scorer.py
   UDP→TCP→DoH     parsers RFC 7208/6376/7489      scoring 0-100 + 8 vectores
        │               │                               │
        └───────┬───────┴───────────┬───────────────────┘
                ▼                   ▼
        core/hardening.py      core/swaks_bridge.py
        hardening + drills     compose_spoof_email() → .eml exacto
        selftest, IMAP         swaks_send() → subprocess swaks + parser
  • DNS — cliente propio RFC 1035: EDNS0(4096) + bit DO, compresión de punteros, fallback UDP→TCP→DoH (dns.google/Cloudflare) con throttle y retry exponencial; DNSSEC detectado por DS + AD + RRSIG/DNSKEY.
  • Mensaje — EmailMessage + formataddr: RFC 2047 solo en el nombre visible; adjuntos como partes base64 multipart/mixed; boundary aleatorio por mensaje.
  • Envío — subprocess.run(argv) con lista de argumentos (nunca shell: imposible inyectar comandos por los campos), fichero temporal 0600 con borrado en finally, --data @fichero para entrega byte a byte.
  • Veredicto — parser de la transcripción: respuestas <~ y errores **; el código del fin-de-DATA decide (el 221 de cierre se descarta).
  • Seguridad — los pines de sesión (X-Mailer: … (authorized drill)) identifican el drill; las contraseñas SMTP/IMAP solo viven en memoria y no se loguean.

📖 Glosario para principiantes

Email spoofingenviar un correo que parece de una dirección ajena manipulando cabeceras. Funciona cuando el dominio suplantado no publica SPF/DKIM/DMARC.
SPF (RFC 7208)registro DNS que lista qué IPs pueden enviar en nombre del dominio. -all rechaza al resto; ~all solo sugiere; ?all no dice nada.
DKIM (RFC 6376)firma criptográfica por mensaje: el servidor emisor firma y el receptor verifica con la clave pública publicada en DNS (selector._domainkey).
DMARC (RFC 7489)política que une SPF+DKIM y decide qué hacer con los fallos: p=none (nada), quarantine (spam) o reject (bloqueo). Incluye informes rua.
Envelope vs From:el sobre (MAIL FROM) lo usa el protocolo SMTP; el From: visible es una cabecera. DMARC exige que coincidan (alineación) — el spoofing clásico los separa.
MXregistro DNS que dice qué servidor recibe el correo del dominio y en qué orden de prioridad.
STARTTLSupgrade de la conexión SMTP a cifrada. Oportunista: si el otro no lo ofrece, se sigue en claro.
MTA-STS / TLS-RPTpolítica que fuerza TLS entre servidores + registro donde recibes informes de fallos TLS.
DNSSECfirma criptográfica de las respuestas DNS (evita que un atacante falsifique tus registros SPF/DMARC en tránsito).
swaks«Swiss Army Knife for SMTP»: CLI de prueba de correo que MailForge ejecuta por detrás para el envío real.
Greylisting (4xx)el servidor pide reintentar la primera vez: técnica anti-spam. Reintenta en minutos.
Drillsimulacro autorizado: mensaje suplantado contra TU dominio para medir tu defensa, como un simulacro de incendio.

⚖️ Uso legítimo

Permitido: analizar tu dominio o dominios con permiso · drills de envío real solo a buzones del dominio analizado · investigación publicada.
Prohibido: dirigir drills a buzones de terceros · suplantar dominios ajenos · phishing · spam.

El envío real a un dominio ajeno sin autorización puede constituir un delito (fraude informático, suplantación de identidad, violación de la LSSI/GDPR según jurisdicción). El guard in-domain de MailForge lo bloquea por diseño; evitarlo deliberadamente es responsabilidad tuya y única.
✅ Este es el mismo enfoque de dmarcian, EasyDMARC o el "spoof test" de MXToolbox: ver el ataque desde la perspectiva del atacante, pero ejecutado por el dueño del dominio sobre su propia infraestructura.
